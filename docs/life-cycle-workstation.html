Execution scope / Local development and cloud delivery

Develop Locally.
Deploy Through Approved Workflows.

Every developer uses the same local development workflow. Repository CI/CD manages shared cloud delivery; each teammate does not need a separate deployment pipeline or production permissions.

Local Development

Develop and verify locally, with required CI and reviews before normal merge. Run the risk-selected tests/evaluations for the app. Container checks apply only where containerized delivery applies. No cloud application deployment is implied.

Local Development + Cloud Delivery

The same local work and CI, plus a verified release package or image, compatible infrastructure and approved application deployment to the selected cloud environments. Cloud deployment is opt-in; required CI is not.

These are activities inside EXECUTE, not additional lifecycle stages: set up the development environment, develop and verify the app, then build and deploy if approved. The repeated edit/build/test/run cycle is the inner loop; shared build and delivery workflows are the outer loop. CI means continuous integration; CD means continuous delivery/deployment. Resume offers only the setup/run or continuation appropriate to the saved stage; Handoff remains a separate export workflow.

  • New project: agree delivery intent during discovery.
  • New iteration: recover configuration and confirm only missing or changed stopping-point decisions.
  • Resume: recover the actual remaining work and shared delivery obligations. Do not ask every teammate to choose an outer loop or silently rewrite the project's release settings.

A developer may complete a local contribution while the project's release remains pending. Local-only work can still require an approved cloud model or other development service. Cloud hosting follows the project's approved shared delivery path; existing versus missing shared resources is a readiness decision, not an additional entry command.

Automation remains observable: disclose planned operations and blockers, reuse valid inputs and request the approvals required by scope, access, spending or production exposure.

SPEC / Discovery interview

Discovery Interview.

Discovery resolves the problem, users, constraints, and acceptance criteria. It does not silently assume your technology or configuration choices.

  • For SDLC and its extensions, answer the independent Discovery, UX and API mode questions after reading the approved seed/intent and before any elicitation or drafting. Autopilot is not an answer to these questions.
  • Complete all four rounds and the applicable configuration interview. Show the actual effective settings and offer Use these settings / Customize settings; resolve changes and required approvals before recording meta/config. A valid covering Autopilot grant may delegate routine configuration choices.
  • Confirm delivery intent, service needs and environment ownership separately. Capture Sequential/Parallel once and reuse that answer at PLAN; configuration alone grants no Parallel authorization.
  • Draft the specification, applicable UX/API requirements, domains and testable acceptance criteria. Instance reuse/creation and executable IaC belong to approved EXECUTE work, not Discovery.

Discovery begins SPEC. New iterations reuse valid context; Resume continues an unfinished interview only when needed for the recovered task.

Reverse Engineering follows its own Discovery-mode selection and investigation/evidence rules, not the SDLC configuration interview or UX/API mode questions. It introduces no application implementation, CI/protection installation into the target or deployment.

Incident / Explicit authority

Fewer Commands.
The Same Incident Safeguards.

Describe an urgent production incident when beginning a change, or use Resume to continue an already authorized incident. TWTTY must recognize the incident path, not treat it as routine feature work or silently create a second incident.

  1. Confirm and authorize the incident.

    Recover the affected production target, scope and inherited controls. Obtain explicit incident approval before changes or incident-owned prerequisite restoration.

  2. Isolate and verify recovery.

Project-owned configuration

Development platform

Development procedure

development: the project-owned development and delivery profile owns dependency/tool readiness, infrastructure-first preparation, app bindings, native runtime, applicable containers and separate Resume setup/run. PLAN references this procedure and records app-specific choices rather than copying it.

Deployment target and identity

cloud binds the provider, not an automatic hosting decision. Profiles cover Azure and no cloud services. A local app may still need Azure: Runtime target: N/A means no cloud application hosting, not cloud: none. Azure guidance is not a bundle of ready-made IaC templates.

Approved technical stack

technical-stack: preferred languages/versions, frameworks, libraries, build/test tooling, UI stack and banned dependencies or patterns. With no stack bound, AI researches appropriate current choices and confirms preferences rather than silently adopting a fixed stack.

Agentic runtime stack

agentic-stack adds the app's agent framework/SDK, model platform and model, orchestration pattern, tool/MCP ecosystem, tracing and guardrails. The agentic binding is distinct from the coding harness and from cloud provisioning/authentication; current SDK/model availability must be verified.

Risk and specialization controls

risk-calibration selects the control ladder and matrices. risk-calibration-delta adds agentic evaluation or data-engineering requirements without discarding baseline controls.

Internal policies

policies: bind the organization's data handling, secrets, access, change-management and retention policies. Policies may strengthen applicable controls, not relax them.

Regulatory overlays

compliance selects confirmed applicable regimes and their controls; it is not an unconditional default. The shipped example bundle selects GDPR and SOC 2. A profile supplies control requirements, not certification.

Engineering guidance

best-practices: agentic development, architecture, API design and testing guidance informs PLAN and execution. Record how the design applies or deviates from it; policy can elevate selected guidance into a requirement.

UX quality policy

ux: accessibility targets, automated/design-quality scans, design skills, prototypes, rendered evidence, themes, usability checks, design-system preference and UX-mode defaults. Apply the selected level's controls to affected surfaces; a local-only target does not waive them.

Reusable capabilities

reusable-assets / skills: inspect the bound directory and load applicable skills. Library and project-captured skills add reusable capability, not authority. Portable library bindings for MCP servers, hooks and prompts remain future extension points; harness-supported integrations are a separate surface.

Build budgets

tokenomics.build: agent tokens, spend and elapsed build time, with optional context/latency advisories. Defaults have no caps. Usage is measured where available; inability to enforce a configured cap must be surfaced, not reported as success.

Product inference budgets

tokenomics.product: the agentic app's separate per-request/session/day budget and degradation policy. Configured ceilings are checked through measured evaluation cost and tested app-runtime controls; defaults have no caps.

Escalation destination

escalation: choose the reachable destination for blocked work, such as a PR comment, issue, Teams, Slack or email. The default configuration records the choice; a channel name does not itself configure or authorize an integration.

Execution defaults

execution-mode, execution-pattern and concurrency-cap default to Interactive, Sequential and at most five SDLC workers. Configuration alone grants no Autopilot or Parallel authority.

Specialization composition

specialization records the selected type. Source overrides metadata identifies the baseline extended by agentic-app and data-engineering addenda. Resolve inheritance during materialization or approved refresh, not as a live runtime fallback chain.

Independent choices and binding boundaries

Discovery, UX and API modes govern who makes the applicable design decisions. Execution mode governs gate approval; execution pattern governs concurrency. Confirm these independently at their defined points. An execution default, budget setting or tool profile does not authorize Autopilot, Parallel dispatch, new access, additional spend or production exposure.

Local Development.
The Developer Inner Loop.

The inner loop runs the application on the developer workstation; it is not limited to native desktop applications. Create or reuse the required local infrastructure and minimum approved cloud services, then edit, build/test and run/debug. A web app can run on the workstation while calling an authorized cloud model.

The approved requirements and PLAN determine which services the local app needs. Use package manifests, lockfiles and existing setup commands to prepare required tools/packages first, then local/cloud services and application connection settings in the approved starting branch. Create app-worker branches and prepare required AI evaluation tests after that foundation; do not require an app build, test harness or model call before creating its required services.

  1. Edit
  2. Build / test
  3. Run / debug
  4. Repeat

Start once and reuse. Functional tests and app-backed evaluations can use the same running application. The final Run means keeping the verified instance available for interactive use, not starting it again. Unit tests and direct in-process evaluations need no app server. Restart only when changes or explicit lifecycle tests require it.

  • Run only applicable risk/policy checks: L1 defaults to an actual happy-path smoke; L2+ or explicitly selected/required verification adds its formal tests/evals. Independent source scans/unit tests can run in parallel without dispatching concurrent writers; image scans require an image.
  • Run required source, secret, dependency and IaC checks locally. CodeQL CLI supports local SAST subject to licensing; GitHub-hosted security enforcement does not become a local service. Do not invent infrastructure-only app tests or additional validation gates.
  • Complete required publication controls and reuse evidence only while its effective inputs remain valid. Local checks do not replace authoritative CI.
  • Use approved synthetic/public inputs, never customer crash reports or binary dumps for setup testing. Obtain required approval for real-model calls.

Where containerized delivery applies, build and verify the image before the PR or when packaging/runtime changes. Keep one application/evaluation implementation across applicable execution paths.

What Does Local Readiness Prove?

Verify actual UI/API/service journeys, not only installed dependencies, health flags or a prototype. An AI-dependent L1 smoke includes a real approved-model response and observed result, not a statistical quality claim; formal quality claims need the applicable measured evaluations. Local execution cannot certify deployed Managed Identity, private cloud networking or production acceptance.

These are logical verification stages, not a requirement to serialize every check or restart services at each stage. The Microsoft Docker inner loop informs the container checkpoint; the native fast loop avoids unnecessary image rebuilds.

Packaging / When containerized delivery applies

Build and Test the Applicable Image.

This checkpoint applies only where containerized delivery is in scope. It does not impose Docker, Compose or emulator setup on every app. Selected support-service containers remain applicable even if the app runs natively; scans/tests follow the active risk/policy requirements.

  1. Build app image
  2. Image scan
  3. Start container
  4. Integration tests
  5. Applicable shared evals

Use the shared version-controlled Dockerfile and build recipe. Local Docker builds a development candidate, catching packaging, startup, dependency and Linux-runtime differences that native execution may miss. Caching, valid existing builds and hot reload keep feedback fast.

Compose under infra/environments/local/ orchestrates the required emulator and app-container services for the checkpoint. Avoid conflicts with the native instance's ports and data; do not stop unrelated apps or delete retained volumes. Verify readiness, then reuse that checkpoint instance for its tests/evals.

Authentication must work inside the container. Host Azure CLI sign-in is not automatically available there. Use an approved development-authentication setup, verify network/DNS access and keep credentials out of the image. Private endpoints require an approved route reachable from the container.

The authoritative release image is built/tested by trusted CI after merge and promoted unchanged through selected cloud environments. That does not prohibit local candidate builds. Development-only credential tooling must not become a dependency of production Managed Identity authentication.

Shared outer loop / Protected CI/CD

Developers Contribute.
Pipelines Deliver.

Developers can change application code, packaging, IaC and pipeline definitions in reviewed worktrees and PRs. After merge, protected workflows execute from the approved branch, normally main. Workflow definitions are merged; pipelines execute the deployments. Merge alone is not production authorization.

CI: Build and Verify Once

PR checks validate the candidate. After protected merge, trusted CI builds/tests and publishes the immutable release artifact, such as a container image where applicable, with its digest and required evidence. Local images are development candidates, not automatically release artifacts.

CD: Promote, Do Not Rebuild

Deploy the same approved digest through selected cloud environments with environment-specific configuration, approvals and acceptance gates. Do not rebuild per environment or depend on a developer's local image.

Separate infrastructure and application CD workflow definitions. Each is independently triggerable. Infrastructure CD validates/applies approved hosting changes or relevant drift after applicable CI promotion checks, preserving app-owned settings; app-only changes do not reapply unchanged infra. Application CD consumes compatible infrastructure and the verified artifact; infra-only changes reuse a valid app artifact without fabricating a new build. When both change, app CD waits for the required compatible infra revision under the environment's locking rules.

If local tests/evals require a new cloud development service, prepare it first through the selected provider's approved infrastructure-code and CLI workflow. Review and commit its definitions without requiring an application release or infrastructure CD for that local-owned dependency. New shared hosting/environment prerequisites still follow infrastructure CI/CD before the dependent application CD. Never pass blocked real-service checks as mocks.

Cloud acceptance verifies the deployed workload identity, networking, real storage/database/model behavior and relevant release requirements that local execution cannot establish. Gates, observability and rollback stay attached to the release.

How GitHub Represents the Workflow

GitHub Actions uses workflows, jobs and steps with explicit dependencies. Independent checks can run in parallel. To reuse a running app for functional tests and app-backed evaluations, group its startup/readiness and those checks in one job. Separate jobs do not automatically share processes. CI cleans up its own temporary runtime; local work may retain the verified app and project-owned service data.

Microsoft deployment supply-chain guidance and GitHub workflow concepts inform these recommendations. The staged presentation is not a universally prescribed serial command sequence.

The Same Evaluations.
Earlier Feedback.

L1 defaults to a live-model smoke, not a formal evaluation harness. Use the normal app journey and approved actual model, safe inputs and required billable-call consent. Record the observed result and available usage/latency/cost evidence; state unavailable measurements honestly. No scored dataset, N-run rule or statistical quality claim is implied. Broader verification requires explicit Human selection or stricter policy, not Delegated discovery or a general Autopilot grant. Keep required runtime safety, privacy and budgets.

When formal verification applies at L2+ or when explicitly selected/required, prepare applicable eval assets after service preparation and before affected LLM behavior. Verify/reuse unchanged assets; do not recreate a harness for every item. Use one application/agent implementation, evaluation engine, approved datasets, thresholds and report schema locally and in cloud. Environment IaC defines resources, not a second evaluation implementation.

Direct evaluations call the shared code in-process and need no app server. API-triggered evaluations use the existing app instance. Cloud execution may use the approved app/job/runner path without requiring one particular cloud compute service.

  • Use deterministic/mock checks for fast feedback, never as required live-model evidence. Do not add a separate connectivity probe or model-call acceptance gate before the normal app journey.
  • For required formal evidence, use the approved N/pass rule, datasets and applicable safety/latency/budget checks. Fast local samples are not final statistical proof.
  • Record actual source/config/model metadata, applicable dataset/evaluator versions, run counts and limitations without secrets or sensitive identifiers. Compare local/cloud scores only under matching effective inputs.
  • Health flags, offline abstention and failed inference never prove a required working model. Do not silently change models, regions, risk thresholds or acceptance criteria.
  • Preserve shared synthetic fixtures where designed. Verify real adapters and deployed identity/network integration where required; one evidence category does not prove another. Default product budgets have no caps; do not invent a cap or tests for an unselected cap.

Keep required cloud-specific checks while shifting applicable tests and real-model evaluations left. Respect the agentic risk/evaluation controls, approved budgets and reproducibility requirements.

Interactive, Autopilot, Parallel, and Delegated Are Not Synonyms
  • Execution mode: Interactive or scoped Autopilot controls who approves eligible work.
  • Execution pattern: Sequential or Parallel controls eligible dispatch; concurrency still respects dependencies and claims.
  • Discovery, UX, and API modes: independent interaction/delegation decisions; applicable UX/API work can be explicitly N/A.

Autopilot never means silently approving new scope, unapproved costs/access, irreversible actions, or required production exposure. Work pickup selection and hotfix entry retain their defined Human approvals.
